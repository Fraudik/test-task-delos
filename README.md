# Тестовое задание Delos

Дизайн документ и сервис для сценария: партнёр создаёт счёт → на адрес приходит перевод USDT →
ждём N подтверждений → AML-проверка → зачисление на баланс за вычетом комиссии или возврат.
Дизайн документ: [design-doc.md](design-doc.md)

## Запуск

```bash
docker compose up --build
```

Поднимаются Postgres и сервис на `http://localhost:8080`. Миграции применяются при старте.

- Swagger UI для ручного прогона: http://localhost:8080/docs (кнопка **Authorize** — API-ключ партнёра).
- Партнёры, их комиссии и черный список AML заданы в config.json. Стандартное количество подтверждений - 5, 
сценарии ниже описаны с учетом этого.

При рестарте продолжается та же цепочка (состояние "сети" и БД персистентны)

## Как проверить сценарии вручную

Каждый сценарий: создать счёт (`POST /v1/invoices` с `{"amount": ...}`), отправить на его адрес перевод на сумму счёта (`POST /sim/transfers`),
дальше — действия из таблицы. Результат смотреть в `GET /v1/invoices/{id}` и `GET /v1/balance`
(через curl или в Swagger на `/docs`).

| Сценарий | Что сделать | Что ожидать |
|---|---|---|
| Зачисление | намайнить 4 блока (`/sim/blocks`) | при 4 подтверждениях `processing`, баланс не тронут; на 5-м `paid`, `available` += сумма − комиссия |
| Возврат | отправитель `0xbad…bad`, 4 блока | `refunded`, баланс не меняется, возврат `ready_to_send` → `initiated` (в логах `InitiateRefund`) |
| AML недоступен | `PUT /sim/aml {"available":false}`, 4 блока, затем `{"available":true}` | сначала `confirmed` и сумма в `on_hold`, после включения `paid` |
| Реорг до подтверждений | 1 блок, затем `/sim/reorg {"depth":2}` | депозит `orphaned`, счёт `awaiting_payment`, ни холда, ни зачисления |
| Реорг, та же транзакция снова | `/sim/reorg {"depth":1,"reinclude":true}`, затем 4 блока | у депозита меняется `block_hash`, депозит один, зачислен один раз |
| Повторная обработка | после зачисления `/sim/rescan {"from_block":0}` | балансы и депозиты не меняются |
| Рестарт | AML выключить, довести до `confirmed`, `docker compose restart app` | после рестарта `paid`, зачислено один раз; `/sim/rescan` после рестарта ничего не меняет |
| Идемпотентность счёта | повторить `POST /v1/invoices` с тем же `Idempotency-Key` | `200` и тот же `id`/`address` |
| Изоляция | запросить счёт одного партнёра ключом другого | `404` |

## Тесты

```bash
docker compose up -d postgres
go test ./...
```

Тесты на базе используют отдельную копию шаблонной БД на каждый тест (`TEST_DATABASE_URL`,
по умолчанию Postgres из compose). `go test -short ./...` пропускает тесты с базой.

## Устройство

| Пакет | Что делает |
|-------|-----------|
| `chain`, `chain/simulator` | интерфейс блокчейна и симулятор с реоргами |
| `aml`, `aml/mock` | интерфейс AML и детерминированный мок |
| `ledger` | двойная запись: журнал проводок + балансы счетов, идемпотентные пакетные проводки |
| `processing` | оркестрация конвейера: конфиг, циклы опроса и оповещения, раздельный запуск сканера и воркеров |
| `processing/scanner` | чтение блоков, курсор, обнаружение депозитов, обработка реоргов |
| `processing/confirmations` | Проверка подтверждений |
| `processing/screening` | AML-проверки с повторами |
| `processing/settlement` | зачисление за вычетом комиссии или возврат |
| `processing/deposit` | общие функции для стадий обработки |
| `notify` | уведомления партнёров: `NotifyPartner` по оплаченным счетам (заглушка) |
| `transfers` | исходящие переводы, в рамках задания только возвраты: `InitiateRefund` (заглушка) |
| `api` | HTTP API партнёра, ручки симулятора, OpenAPI + Swagger UI |
| `postgres` | подключение и миграции (goose) |

Стадии работают независимо и параллельно, каждую можно запускать на нескольких репликах кроме сканера.

## Гарантии и где они обеспечены

- **Нет двойного зачисления**: `UNIQUE (tx_hash, log_index)` у депозита, ключ идемпотентности у проводок.
- **Деньги не на балансе до ответа AML**: при N подтверждениях сумма идёт только в `hold`; в `available` —
  только стадией завершения при записанном низком риске; триггер в БД запрещает `credited` без `low`.
- **Откат блока до N подтверждений**: в ledger до N подтверждений ничего не пишется; сканер хранит хэши
  прочитанных блоков, при расхождении идёт вниз до последнего совпадающего, откатывает курсор к нему и переводит
  депозиты из замененных блоков в `orphaned`.
- **Никаких float**: суммы — `int64` в микро-USDT (6 знаков), в API — десятичные строки; комиссия считается
  в целых числах, округление вниз в пользу партнёра.
- **Идемпотентность создания счёта**: `UNIQUE (partner_id, idempotency_key)` + `INSERT ... ON CONFLICT DO NOTHING`;
  параллельные запросы с одним ключом создают один счёт.
- **Изоляция партнёров**: партнёр определяется по API-ключу (в БД хранится SHA-256), все выборки фильтруются
  по его `partner_id`, чужой счёт — 404.

## Допущения и упрощения

Сканер один, других реплик нет. Остальные этапы обработки задизайнены под несколько реплик, но тоже запускаются только с одной. Счета без временного лимита, переплаты не обрабатываются. Все запускается в одном сервисе. Метрик и трейсинга нет. 
Для комиссий нет тарифов, зафиксированы у партнеров.

Допущения сделаны либо в рамках задания, либо для упрощения деталей, не напрямую затрагивающих ключевой сценарий (как тарифы комиссий).
Сервисы запущены в одном приложении для упрощения и ускорения. Нет отдельной системы проверки уникальности uuid счетов и их выдачи (потребуется только на больших масштабах).

Для удобства тестирования методы по счетам возвращают доп. информацию о переводах, в реальной системе этого не будет.

## Как я использовал AI

**В коде:**
Для testdb, написания тестов, консультации по коду, генерации шаблонных сценариев (вроде ретраев), написания моков уведомлений и возвратов и добавления Swagger.
А также для рефакторинга в конце. Для него зафиксировал сценарии и просил проверять по ним.
AI хотел проверять состояние сети в моменте проверки подтверждений (вне сканера), считая, что блоки могут появиться вне запусков сканера.
Все проводки по переводам AI предлагал делать по одному для коротких транзакций, при батчевой обработке переводов не стал добавлять сбойные переводы в needs_review.
Упустил, что счета могут оплачиваться больше, чем одним переводом. Хотел выдавать пользователю последовательные численные  ID из БД, поменял на uuidv4.

**В документе:**
Узнавал детали и нюансы работы с Ethereum сетью, про адреса, форвардеры. Спрашивал критику. 
AI предлагал shared wallet, где каждому клиенту мы будем выставлять сумму с каким-то уникальным небольшим хвостом. Но я решил, что это ненадежная система.

В Readme попросил сгенерировать сценарии и устройство, попутно тоже проверив.
